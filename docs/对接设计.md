# 对接设计

## 目标

把 PC 微信的自动回复交给常驻 Hermes 智能体，同时保留「Hermes 主动找人说话」的能力——
后者是纯请求-响应模型做不到的。

---

## 关键设计决策

### 1. 感知与生成彻底解耦

感知层（OCR + 像素）只负责「谁说了什么」，不碰任何 LLM 逻辑。
生成交给 Hermes。

好处：换模型、改人设、换后端，感知层一行不动。

### 2. 每联系人一个 Hermes session

Bridge 维护 `联系人 → session_id` 映射（`wechat_convo_map.json`）：

```json
{ "张三": "api_1791563112_fdce742a" }
```

- **天然隔离**：不自己拼 prompt 数组，不会有串线
- **持久化**：进程重启后会话不丢
- **独立上下文**：每个人的历史互不可见

首次接触某人时 `POST /api/sessions {"title": "微信-<联系人>"}` 建会话。
title 唯一，重复会 400 `invalid_title`——`_find_session_by_title()` 负责找回复用。

### 3. Bridge 嵌在 bot 进程内

Bridge 和 OCR bot 都操作微信窗口（鼠标键盘），必须串行化。
同进程可以直接共用一个 `SendQueue`；拆开要多设计一套跨进程互斥。

Bridge 自身只做 HTTP 和 JSON 处理，零额外依赖（标准库 `http.server`），
与 bot 的技术栈一致。

### 4. 通信用 HTTP 而非 import

bot 跑在 Python 3.8（Miniconda），Hermes 在 3.11（自己的 venv）。
rapidocr / opencv / onnxruntime 这些 C 扩展跨版本不保证 ABI 兼容，
强行 import 属于定时炸弹。

HTTP loopback 往返亚毫秒级，相比 agent 数秒的推理开销可忽略；
换来的是稳定的契约边界——协议不变，bot 内部怎么重构都不影响调用方。

### 5. 三级降级

```
Bridge（API Server）  →  Hermes CLI  →  OpenAI 兼容 API  →  兜底话术
  首选                  12 秒         需外部服务
```

任何一层失败自动降级，永不阻塞微信回复。日志会明确标出走的是哪条路：

| 日志标记 | 走的路径 |
|---------|---------|
| `🌉 [Bridge] 转发给 Hermes` | API Server（正常） |
| `🤖 [Hermes] 调用 CLI` | 降级到 CLI |
| `🤖 [Fallback] 调用大模型` | 降级到 OpenAI API |

### 6. 主动推送用插件工具

Hermes 侧通过目录插件 `~/.hermes/plugins/wechat_bridge/` 提供两个工具：

| 工具 | 作用 |
|------|------|
| `wechat_send(contact, text)` | 主动发消息 |
| `wechat_status()` | 查会话映射 |

`check_fn` 探测 Bridge 是否在线——不在线时工具对模型完全隐藏，
避免 agent 撞一堵墙后瞎猜。

### 7. GIL 隔离

bot 主循环每 0.5 秒跑一次 OCR（几百毫秒 CPU 密集），会饿死其他线程。
因此 `/health` **不碰网络**，只报自身存活；Hermes 状态由后台线程每 15 秒
刷新缓存，`/hermes` 读缓存返回。

### 8. Windows 端口独占

`ThreadingHTTPServer.allow_reuse_address = True` 会让重复 bind 的僵尸进程
也显示 `LISTENING`，连接随机落到死进程。设为 `False` 并显式 `server_close()`。

## 会话隔离的实现

```
API_CONVERSATION_HISTORY = {}      # bot 内存（仅 CLI 降级路径用）
SessionMap                         # 联系人 → Hermes session_id（落盘）
         ↓
   POST /api/sessions/{id}/chat
```

正常路径（Bridge）由 Hermes 侧维护上下文，bot 不碰历史。
只有降级到 CLI 时才用 `API_CONVERSATION_HISTORY`，那里也按 sender 分桶。

## 发送队列

所有 GUI 操作（`send_reply_instant`）必须串行——多线程同时动鼠标键盘必然出错。

```python
class SendQueue:
    def submit(self, contact, text): self._q.put((contact, text))
    def _run(self):
        while True:
            contact, text = self._q.get()
            self._sender(contact, text)   # 复用 bot 的 GUI 链路
```

被动应答和主动推送共用这一条队列。

## 附录：被废弃的方案

以下方案评估后放弃，记录在此避免重复踩坑。

### A. CLI 子进程调用

`hermes chat -q` 每次 fork 新进程，12 秒延迟，Hermes 的 memory / skills / tools
全部用不上，只能做纯文本生成。且请求-响应模型下无法实现主动推送。

### B. 插件直接 import bot

依赖环境不兼容（3.11 vs 3.8），C 扩展跨版本 ABI 有风险。
且耦合方向错误：import 让工具依赖 bot 源码，改函数签名即崩。

### C. 往 `tools/` 目录塞工具

`tools/` 是 Hermes 核心树，`hermes update` 会覆盖，
且需同步改 `toolsets.py` 的 `_HERMES_CORE_TOOLS`。
官方文档明确要求第三方集成走 `plugins/`。

### D. Bridge 独立进程

需跨进程互斥 GUI 操作，反而增加复杂度。

## 附录：踩坑记录

完整清单见 Hermes skill `hermes-custom-tool-playbook`（跨项目通用）。
本项目相关的六条：

| # | 现象 | 根因 | 处理 |
|---|------|------|------|
| 1 | 白名单读到默认值 | `load_config()` 写死读 `wechat_config_dev.json`，`--config` 参数无效 | 写对文件名 |
| 2 | CLI 报 usage 错误 | 多行 prompt 传给 `-q` 被 shell 拆散 | 改用 `--query-file` |
| 3 | CLI 仍报 usage | PATH 有 5 个 hermes，命中旧版（无 `--query-file`） | 配置写绝对路径 + `shell=False` |
| 4 | `UnicodeDecodeError` | Windows GBK 解码 UTF-8 输出 | `encoding="utf-8", errors="replace"` |
| 5 | Bridge 请求无响应 | 同步调 Hermes，被 OCR 主循环饿死 GIL | 改后台缓存 |
| 6 | session id 解析失败 | id 嵌在 `session` 对象里，不是响应顶层 | 兼容多级取值 |

另有两个 API Server 响应结构的坑：
- `POST /api/sessions` → `{"session": {"id": ...}}`（不是顶层 `id`）
- `POST /api/sessions/{id}/chat` → `{"message": {"content": ...}}`
